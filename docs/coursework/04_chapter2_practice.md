### 2.4.2 Исключение известных тем

По ответам диагностического теста класс `KnowledgeEstimator` определяет известные темы. Верный ответ по теме означает, что пользователь знает и саму тему, и все её предшествующие темы: кто правильно ответил о Riverpod, знает и основы Dart. Предшественники находятся обходом графа в глубину. Неверный ответ или «Не знаю» исключает тему из известных, даже если её «покрыл» верный ответ по более сложной теме: явный провал важнее косвенного вывода.

### 2.4.3 Топологическая сортировка

Темы образуют ориентированный граф: ребро «A → B» означает, что тему B нельзя изучать раньше темы A. Порядок изучения — это топологическая сортировка графа, которая выполняется алгоритмом Кана [1; 6]:

1. Для каждой темы считается входящая степень — число её зависимостей внутри плана. Зависимость, которой нет в плане (тема уже известна), считается выполненной.
2. Темы с нулевой степенью помещаются в очередь.
3. Из очереди извлекается тема и добавляется в результат; у всех зависящих от неё тем степень уменьшается на единицу, и темы с нулевой степенью попадают в очередь.
4. Если в результат попали не все темы, в графе есть цикл, и алгоритм сообщает, какие темы в него входят.

Чтобы результат был одинаковым при одинаковых данных, очередь упорядочена по уровню сложности темы, а при равном уровне — по позиции темы в каталоге. Для этого используется упорядоченное множество `SplayTreeSet`, поэтому сложность алгоритма — O((V + E) · log V), где V — число тем, E — число зависимостей. Для каталога из 20 тем это мгновенно. Фрагмент реализации:

```dart
final queue = SplayTreeSet<int>(compare);
for (var i = 0; i < topics.length; i++) {
  if (inDegree[i] == 0) queue.add(i);
}
final result = <Topic>[];
while (queue.isNotEmpty) {
  final current = queue.first;
  queue.remove(current);
  result.add(topics[current]);
  for (final next in dependents[current]) {
    inDegree[next]--;
    if (inDegree[next] == 0) queue.add(next);
  }
}
if (result.length != topics.length) throw CycleDetectedException(...);
```

### 2.4.4 Раскладка по дням и интервальные повторения

Класс `Scheduler` моделирует календарь день за днём, начиная с даты старта:

1. Дни недели, не выбранные пользователем, пропускаются.
2. Дневной лимит равен часам в неделю, делённым на число учебных дней. Он округляется до 15 минут и не бывает меньше 30 минут.
3. В начале дня ставятся повторения, срок которых наступил, по 15 минут каждое.
4. Оставшееся время заполняется текущей темой. Тема может делиться на части, но часть не бывает короче 30 минут, если тема на ней не заканчивается: короткие обрывки неудобны для занятия.
5. Когда тема изучена полностью, планируются её повторения через 1, 3 и 7 календарных дней. Интервалы выбраны по кривой забывания Эббингауза [5] и исследованиям распределённого повторения [3]. Повторение, выпавшее на неучебный день, переносится на ближайший учебный.

### 2.4.5 Проверка дедлайна

Датой окончания плана считается день последнего занятия по новой теме (повторения после него не учитываются). Если дата окончания позже дедлайна, генератор подбирает минимальное число часов в неделю, при котором план укладывается в срок: значения перебираются с шагом 0,5 часа до 84 часов в неделю (12 часов × 7 дней). Если не хватает даже 84 часов, пользователю предлагается перенести дедлайн.

### 2.4.7 Перепланирование

Если пользователь пропустил занятия или изменил расписание, класс `Replanner` перестраивает план. Выполненные занятия остаются на своих местах. Для каждой темы считается, сколько минут уже изучено, и остаток заново раскладывается начиная с сегодняшнего дня по тем же правилам. Невыполненные повторения уже изученных тем переносятся на ближайшие учебные дни. Номера частей продолжают уже выполненные части. После перестройки снова проверяется дедлайн.

Доступ к экранам проверяет одна функция `authRedirect`, которую go_router вызывает перед каждым переходом:

```dart
String? authRedirect(AuthStatus status, String location) {
  if (status == AuthStatus.unknown) {
    return location == '/splash' ? null : '/splash';
  }
  final loggedIn = status == AuthStatus.authenticated;
  final isPublic = publicRoutes.contains(location);
  if (!loggedIn) return isPublic ? null : '/login';
  if (isPublic || location == '/splash') return '/home';
  return null;
}
```

Пока сессия проверяется, виден только Splash; без входа доступны только вход и регистрация; после входа экраны входа ведут на главную. Роутер подписан на состояние авторизации, поэтому выход из аккаунта или его удаление сразу открывают экран входа.

### 2.5.2 Оформление

Интерфейс построен на Material 3 [31]. Цветовая схема создаётся из фирменного тёмно-синего цвета (#1A3A8F), акцентный цвет — оранжевый (#F57C00). Есть светлая и тёмная темы; пользователь выбирает светлую, тёмную или системную тему в профиле. Стили текста строятся от типографики темы, поэтому шрифт и размеры одинаковы на всех экранах. Логотип «М» в виде линии маршрута нарисован кодом (`AppLogo`), иконки приложения для всех платформ генерируются из того же рисунка (`tool/icons/generate_icons.py`).

Пустые состояния (нет плана, нет заметок, ничего не найдено) показывают пояснение и кнопку следующего действия. Ошибки ввода выводятся под полями форм, ошибки операций — во всплывающих сообщениях. Необратимые действия (удаление плана, темы, заметки, выход, удаление аккаунта) требуют подтверждения.

### 2.5.3 Адаптивность

На широком экране (от 840 логических пикселей, класс «расширенное окно» по рекомендациям Android [43]) нижняя панель вкладок заменяется боковой (`NavigationRail`), а содержимое экранов ограничивается колонкой шириной 720 пикселей по центру, чтобы строки текста не растягивались на весь монитор. Работа на телефоне в обеих ориентациях и в окне 1280×800 проверяется автоматическим тестом (раздел 2.7). Подписи вкладок не увеличиваются вместе с системным шрифтом, чтобы «Статистика» не переносилась по буквам, а остальной текст масштабируется. Перед сдачей все экраны дополнительно сняты в семи вариантах: светлая и тёмная тема, маленький телефон 360×640, крупный шрифт 130 %, горизонтальная ориентация и окно компьютера; по этим снимкам исправлено десять недочётов (ошибки № 13–22 в разделе о тестировании).

## 2.6 Реализация основных модулей

### 2.6.1 Регистрация, вход и хранение паролей

Учётные записи хранятся в таблице `users`. При регистрации имя очищается от лишних пробелов, email приводится к нижнему регистру и проверяется на уникальность. Пароль должен быть не короче 8 символов и содержать буквы и цифры.

В версии 1 семестра пароль хранился как SHA-256 от соли и пароля. SHA-256 вычисляется очень быстро, поэтому при копировании файла базы простые пароли можно подобрать перебором. Во 2 семестре хранение переведено на PBKDF2-HMAC-SHA256 [36], одну из функций, которые для паролей рекомендует OWASP [33]:

- соль — 16 случайных байт из криптостойкого генератора `Random.secure()`;
- функция HMAC-SHA256 применяется 100 000 раз, что во столько же раз замедляет перебор;
- результат хранится в виде `pbkdf2_sha256$100000$<хэш>`: число итераций записано в самом хэше, поэтому его можно увеличить в следующей версии, и старые записи продолжат проверяться;
- сравнение хэшей выполняется за постоянное время, чтобы время проверки не подсказывало, сколько символов совпало;
- расчёт выполняется в отдельном изоляте (`compute`), поэтому интерфейс не замирает на время входа.

Пользователи, зарегистрированные в версии 1 семестра, не теряют доступ: при входе приложение определяет формат хэша, проверяет пароль старым способом и сразу сохраняет новый хэш PBKDF2 с новой солью. Пароль известен приложению только в момент входа, поэтому пересчитать хэши заранее нельзя.

Корректность реализации PBKDF2 проверена по эталонным значениям, которые независимо посчитаны функцией `hashlib.pbkdf2_hmac` языка Python, в том числе для пароля на кириллице. Полный текст класса приведён в приложении Б.

При неверном пароле и при неизвестном email выводится одно и то же сообщение «Неверный email или пароль», чтобы по ответу нельзя было узнать, зарегистрирован ли адрес.

### 2.6.2 Сессия и выход

Если при входе отмечено «Запомнить меня», идентификатор пользователя сохраняется в `shared_preferences`. При следующем запуске Splash проверяет его: если пользователь существует, открывается главная, иначе — экран входа (это защищает от сессии удалённого аккаунта). При выходе идентификатор удаляется, ежедневное напоминание отменяется, а роутер открывает экран входа.

### 2.6.3 Удаление аккаунта

Удаление аккаунта необратимо, поэтому требует повторного ввода пароля. После проверки пароля удаляется строка пользователя, а планы, занятия, темы, заметки, избранное и история Pomodoro удаляются каскадно правилами внешних ключей. Затем выполняется выход.

### 2.6.4 Создание плана и работа с ним

Онбординг ведёт контроллер `OnboardingController`: он хранит выбранное направление, ответы теста и настройки расписания между шагами. На экране предпросмотра `PlanService.preview` рассчитывает план без сохранения, а `PlanService.createPlan` сохраняет темы и занятия в одной транзакции и делает новый план активным. Отметка занятия меняет одну строку таблицы `sessions`; главная, план и статистика получают изменение через потоки drift и обновляются сами.

### 2.6.5 Напоминания и уведомления

Ежедневное напоминание реализовано пакетом flutter_local_notifications [26]. Время напоминания хранится в профиле пользователя и пересчитывается в UTC, поэтому дополнительный пакет определения часового пояса не нужен. При окончании интервала Pomodoro показывается мгновенное уведомление. В Android-проекте объявлены приёмники плагина для показа запланированных уведомлений и их восстановления после перезагрузки, разрешение `RECEIVE_BOOT_COMPLETED` и белый значок уведомлений. На Windows плагин не поддерживает ежедневное повторение без установщика MSIX, поэтому переключатель напоминания в настольной версии недоступен и подписан «Доступно в версии для Android и iOS»; мгновенные уведомления работают.

Сервис уведомлений скрыт за интерфейсом `ReminderService`. В тестах вместо него подставляется заглушка, которая записывает вызовы в журнал, поэтому тесты проверяют, что напоминание запланировано, не показывая настоящих уведомлений.

### 2.6.6 Обработка ошибок

Ошибки, понятные пользователю (занятый email, неверный пароль, пустое название), передаются исключением `AppException` с русским текстом и выводятся под полем формы или во всплывающем сообщении. Повреждённый файл каталога превращается в понятное сообщение вместо падения приложения. Ошибки платформы при работе с уведомлениями не прерывают выход из аккаунта.

## 2.8 Сборка и развёртывание

Сборка автоматизирована в GitHub Actions [27] (файл `.github/workflows/build.yml`). При каждой отправке кода в репозиторий выполняются:

1. проверка форматирования кода, статический анализ и все модульные и виджет-тесты;
2. интеграционный тест настоящего приложения в Linux на виртуальном экране;
3. сборка релизного APK для Android (`flutter build apk --release`) [19];
4. сборка релизной версии для Windows (`flutter build windows --release`) [20].

Готовые файлы сохраняются как артефакты сборки. Когда на странице Releases репозитория публикуется новый релиз (например, `v1.0.0`), сборка запускается для него и прикладывает APK и архив для Windows к релизу, откуда их можно скачать без входа в GitHub.

Для установки на телефон нужно скачать файл `marshrut-release.apk`, открыть его и разрешить установку из этого источника. Релизный APK подписан отладочным ключом: для установки на свой телефон этого достаточно, для публикации в Google Play нужен собственный ключ подписи. Версия для Windows распространяется как архив: его нужно распаковать и запустить `marshrut.exe`. Для самостоятельной сборки достаточно установленного Flutter SDK: команды приведены в README.
