## 2.2 Архитектура приложения

Система состоит из двух программ: мобильного приложения и сервера API (рисунок 2.1). Приложение построено по принципам чистой архитектуры [2] и рекомендациям команды Flutter по архитектуре приложений [22] и разделено на три слоя. Сервер написан на том же языке Dart и использует общие с приложением сущности, правила проверки данных и формат JSON.

Рисунок 2.1 — Архитектура: приложение, сервер API и база данных

1. **Слой предметной области** (`lib/domain`) написан на чистом Dart и не зависит от Flutter и базы данных. В нём находятся сущности (тема, план, занятие, настройки расписания), алгоритм построения плана и интерфейсы репозиториев, то есть описание того, какие данные нужны алгоритмам, без указания, где они хранятся. Поэтому алгоритм проверяется обычными модульными тестами за доли секунды.
2. **Слой данных** (`lib/data`) реализует интерфейсы репозиториев. В приложении используются репозитории из папки `lib/data/api`: каждый метод отправляет запрос к серверу через общий клиент `ApiClient`. Таблицы drift и репозитории для работы с базой (`lib/data/db`, `lib/data/repositories`) используются на сервере. Здесь же чтение каталога, уведомления и хранение сессии в `shared_preferences`.
3. **Слой представления** (`lib/presentation`) содержит экраны и провайдеры Riverpod, которые связывают экраны с данными.
4. **Сервер API** (`lib/server/api_server.dart`, программа запуска `bin/marshrut_server.dart`) принимает запросы, проверяет токен и данные и работает с базой SQLite (п. 2.3.2).

Зависимости направлены внутрь: экраны знают о предметной области, слой данных реализует её интерфейсы, а предметная область ни от кого не зависит. Это подтвердилось на практике: при переходе от локальной базы на телефоне к серверу API в приложении заменились только реализации репозиториев, а алгоритм и экраны остались прежними.

Каталог направлений не хранится в базе: это JSON-файлы в папке `assets/catalog/`. Каждая тема описана идентификатором, названием, описанием, трудоёмкостью в часах, уровнем сложности (1–6), категорией, списком зависимостей, ссылками на материалы и, для части тем, вопросом диагностического теста. Такой формат позволяет добавить новое направление без изменения кода. В каталоге 4 направления: «Flutter-разработчик» (20 тем), «Python с нуля» (18), «Английский A1–B1» (19) и «Алгоритмы и структуры данных» (18); всего 75 тем, 113 зависимостей и 32 вопроса.

### 2.3.2 API сервера

Сервер API — программа на Dart (`bin/marshrut_server.dart`), которая запускается на компьютере и принимает запросы по протоколу HTTP на порту 8080. Обработчики запросов собраны в классе `ApiServer` (`lib/server/api_server.dart`), построенном на библиотеке shelf [44]. Каждый запрос проходит цепочку обработки:

1. **журнал** — после ответа в окно сервера записывается строка: время, метод, адрес, код ответа и время обработки;
2. **перехват ошибок** — любое исключение превращается в ответ JSON с кодом ошибки (коды перечислены ниже), подробности непредвиденных ошибок попадают только в журнал сервера;
3. **маршрутизатор** (shelf_router) — по методу и адресу выбирает обработчик;
4. **обработчик** — определяет пользователя по токену, читает и проверяет JSON-тело запроса, проверяет, что запись принадлежит этому пользователю, вызывает репозиторий drift и формирует ответ.

Пример запроса на создание заметки и ответа сервера:

```text
POST /api/notes
Authorization: Bearer <токен>
Content-Type: application/json

{"title": "Списки в Python", "body": "append добавляет элемент в конец"}

HTTP/1.1 201 Created
{"id": 1}
```

Сервер отвечает кодами HTTP [41], а текст ошибки передаёт в поле `error`:

- `200 OK` — данные получены или изменены; `201 Created` — запись создана, в ответе её номер; `204 No Content` — действие выполнено, тело ответа пустое;
- `400 Bad Request` — неверные данные: тело не в формате JSON, нет обязательного поля, поле другого типа, нарушено правило проверки («Введите корректный email…»), занятый email, неверный пароль;
- `401 Unauthorized` — нет токена, токен неизвестен, устарел (действует 30 дней) или удалён при выходе;
- `404 Not Found` — запись не найдена или принадлежит другому пользователю: сервер не сообщает, что чужая запись существует;
- `500 Internal Server Error` — непредвиденная ошибка, например сбой базы; приложение получает только общий текст.

Меры защиты на сервере:

- пароль хранится как хэш PBKDF2 с солью (п. 2.6.1), токен — как хэш SHA-256 [8], поэтому копия файла базы не даёт ни паролей, ни действующих токенов;
- токен — 32 случайных байта из криптостойкого генератора `Random.secure()`, при выходе он удаляется из базы;
- сервер повторно проверяет все поля теми же функциями `Validators`, что и формы приложения, поэтому неверные данные не попадут в базу, даже если запрос отправлен в обход приложения;
- каждый обработчик проверяет владельца записи, поэтому пользователь не может прочитать, изменить или удалить чужой план, заметку или тему, даже зная её номер.

### 2.3.3 Работа приложения с API и обработка ошибок

Все запросы приложения проходят через класс `ApiClient` (`lib/data/api/api_client.dart`), построенный на пакете http [31]. Он приводит адрес сервера к виду `http://хост:порт`, добавляет к запросу заголовок `Authorization: Bearer <токен>`, переводит тело в JSON, ждёт ответ не дольше 10 секунд и разбирает ответ в кодировке UTF-8. Любая неудача превращается в исключение с понятным русским текстом:

- сервер выключен, нет сети или неверный адрес — «Нет связи с сервером … Проверьте, что сервер запущен и телефон в той же сети Wi-Fi»;
- сервер не ответил за 10 секунд — «Сервер … не отвечает»;
- ответ с кодом 4xx или 5xx — текст из поля `error` ответа сервера;
- ответ не в формате JSON — сообщение с кодом ответа;
- ответ `401` — дополнительно вызывается обработчик `onUnauthorized`: контроллер авторизации выполняет выход, и роутер открывает экран входа.

Репозитории приложения (`ApiPlanRepository`, `ApiNoteRepository` и другие) реализуют те же интерфейсы, что и прежние репозитории базы данных. Ответ `404` там, где интерфейс допускает отсутствие записи, превращается в `null`, поэтому экраны не потребовали изменений.

Ошибки показываются пользователю двумя способами. Если не загрузились данные экрана, вместо них выводится сообщение об ошибке с кнопкой «Повторить». Если не удалось действие (сохранение, удаление, отметка занятия, избранное), общая функция `runAction` показывает красное всплывающее сообщение с причиной, а данные остаются прежними. Встроенный в Riverpod автоматический повтор упавших запросов отключён: иначе при выключенном сервере экран около 40 секунд показывал бы загрузку вместо понятной ошибки.

Чтобы экраны обновлялись сами, клиент API после каждого успешного запроса на изменение (`POST`, `PUT`, `PATCH`, `DELETE`) отправляет событие «данные изменились». Потоки данных, созданные методом `ApiClient.watch`, по этому событию загружают данные заново, а после ошибки сами повторяют запрос через 5 секунд. Когда экран закрывается, поток отписывается от событий и отменяет повтор.

Адрес сервера вводится на экране входа кнопкой «Сервер: …» (рисунок 2.30). Перед сохранением приложение отправляет запрос `GET /api/health` и сохраняет адрес, только если ответил именно сервер «Маршрута». Для работы по протоколу HTTP в локальной сети в Android-приложении объявлено разрешение `INTERNET` и разрешён нешифрованный трафик, а в iOS-приложении — подключения в локальной сети с пояснением для запроса разрешения. Для учебного проекта в локальной сети этого достаточно; при размещении сервера в интернете запросы нужно передавать по HTTPS.

### 2.4.2 Исключение известных тем

По ответам диагностического теста класс `KnowledgeEstimator` определяет известные темы. Верный ответ по теме означает, что пользователь знает и саму тему, и все её предшествующие темы: кто правильно ответил о Riverpod, знает и основы Dart. Предшественники находятся обходом графа в глубину. Неверный ответ или «Не знаю» исключает тему из известных, даже если её «покрыл» верный ответ по более сложной теме: явный провал важнее косвенного вывода.

### 2.4.3 Топологическая сортировка

Темы образуют ориентированный граф: ребро «A → B» означает, что тему B нельзя изучать раньше темы A. Порядок изучения — это топологическая сортировка графа, которая выполняется алгоритмом Кана [1; 6]:

1. Для каждой темы считается входящая степень — число её зависимостей внутри плана. Зависимость, которой нет в плане (тема уже известна), считается выполненной.
2. Темы с нулевой степенью помещаются в очередь.
3. Из очереди извлекается тема и добавляется в результат; у всех зависящих от неё тем степень уменьшается на единицу, и темы с нулевой степенью попадают в очередь.
4. Если в результат попали не все темы, в графе есть цикл, и алгоритм сообщает, какие темы в него входят.

Чтобы результат был одинаковым при одинаковых данных, очередь упорядочена по уровню сложности темы, а при равном уровне — по позиции темы в каталоге. Для этого используется упорядоченное множество `SplayTreeSet`, поэтому сложность алгоритма — O((V + E) · log V), где V — число тем, E — число зависимостей. Для каталога из 20 тем это мгновенно. Фрагмент реализации:

```dart
final queue = SplayTreeSet<int>(compare);
for (var i = 0; i < topics.length; i++) {
  if (inDegree[i] == 0) queue.add(i);
}
final result = <Topic>[];
while (queue.isNotEmpty) {
  final current = queue.first;
  queue.remove(current);
  result.add(topics[current]);
  for (final next in dependents[current]) {
    inDegree[next]--;
    if (inDegree[next] == 0) queue.add(next);
  }
}
if (result.length != topics.length) throw CycleDetectedException(...);
```

Полный текст функции приведён в приложении А.

### 2.4.4 Раскладка по дням и интервальные повторения

Класс `Scheduler` моделирует календарь день за днём, начиная с даты старта:

1. Дни недели, не выбранные пользователем, пропускаются.
2. Дневной лимит равен часам в неделю, делённым на число учебных дней. Он округляется до 15 минут и не бывает меньше 30 минут.
3. В начале дня ставятся повторения, срок которых наступил, по 15 минут каждое.
4. Оставшееся время заполняется текущей темой. Тема может делиться на части, но часть не бывает короче 30 минут, если тема на ней не заканчивается: короткие обрывки неудобны для занятия.
5. Когда тема изучена полностью, планируются её повторения через 1, 3 и 7 календарных дней. Интервалы выбраны по кривой забывания Эббингауза [5] и исследованиям распределённого повторения [3]. Повторение, выпавшее на неучебный день, переносится на ближайший учебный.

### 2.4.5 Проверка дедлайна

Датой окончания плана считается день последнего занятия по новой теме (повторения после него не учитываются). Если дата окончания позже дедлайна, генератор подбирает минимальное число часов в неделю, при котором план укладывается в срок: значения перебираются с шагом 0,5 часа до 84 часов в неделю (12 часов × 7 дней). Если не хватает даже 84 часов, пользователю предлагается перенести дедлайн.

### 2.4.7 Перепланирование

Если пользователь пропустил занятия или изменил расписание, класс `Replanner` перестраивает план. Выполненные занятия остаются на своих местах. Для каждой темы считается, сколько минут уже изучено, и остаток заново раскладывается начиная с сегодняшнего дня по тем же правилам. Невыполненные повторения уже изученных тем переносятся на ближайшие учебные дни. Номера частей продолжают уже выполненные части. После перестройки снова проверяется дедлайн.

Доступ к экранам проверяет одна функция `authRedirect`, которую go_router вызывает перед каждым переходом:

```dart
String? authRedirect(AuthStatus status, String location) {
  if (status == AuthStatus.unknown) {
    return location == '/splash' ? null : '/splash';
  }
  final loggedIn = status == AuthStatus.authenticated;
  final isPublic = publicRoutes.contains(location);
  if (!loggedIn) return isPublic ? null : '/login';
  if (isPublic || location == '/splash') return '/home';
  return null;
}
```

Пока сессия проверяется, виден только Splash; без входа доступны только вход и регистрация; после входа экраны входа ведут на главную. Роутер подписан на состояние авторизации, поэтому выход из аккаунта или его удаление сразу открывают экран входа.

### 2.5.2 Оформление

Интерфейс построен на Material 3 [33]. Цветовая схема создаётся из фирменного тёмно-синего цвета (#1A3A8F), акцентный цвет — оранжевый (#F57C00). На широком экране (от 840 логических пикселей, класс «расширенное окно» по рекомендациям Android [50]) нижняя панель вкладок заменяется боковой (`NavigationRail`), а содержимое экранов ограничивается колонкой шириной 720 пикселей по центру, чтобы строки текста не растягивались на весь монитор. ## 2.6 Реализация основных модулей

### 2.6.1 Регистрация, вход и хранение паролей

Учётные записи хранятся в таблице `users` на сервере. Регистрация и вход — запросы `POST /api/auth/register` и `POST /api/auth/login`; пароль проверяет и хэширует только сервер, приложение его не хранит. При регистрации имя очищается от лишних пробелов, email приводится к нижнему регистру и проверяется на уникальность. Пароль должен быть не короче 8 символов и содержать буквы и цифры.

В версии 1 семестра пароль хранился как SHA-256 от соли и пароля. SHA-256 вычисляется очень быстро, поэтому при копировании файла базы простые пароли можно подобрать перебором. Во 2 семестре хранение переведено на PBKDF2-HMAC-SHA256 [39], одну из функций, которые для паролей рекомендует OWASP [35]:

- соль — 16 случайных байт из криптостойкого генератора `Random.secure()`;
- функция HMAC-SHA256 применяется 100 000 раз, что во столько же раз замедляет перебор;
- результат хранится в виде `pbkdf2_sha256$100000$<хэш>`: число итераций записано в самом хэше, поэтому его можно увеличить в следующей версии, и старые записи продолжат проверяться;
- сравнение хэшей выполняется за постоянное время, чтобы время проверки не подсказывало, сколько символов совпало;
- расчёт выполняется в отдельном изоляте (`Isolate.run`), поэтому сервер продолжает отвечать на другие запросы, пока считается хэш.

Пользователи, зарегистрированные в версии 1 семестра, не теряют доступ: при входе сервер определяет формат хэша, проверяет пароль старым способом и сразу сохраняет новый хэш PBKDF2 с новой солью. Пароль известен серверу только в момент входа, поэтому пересчитать хэши заранее нельзя.

Корректность реализации PBKDF2 проверена по эталонным значениям, которые независимо посчитаны функцией `hashlib.pbkdf2_hmac` языка Python, в том числе для пароля на кириллице. Полный текст класса приведён в приложении Б.

При неверном пароле и при неизвестном email сервер возвращает одно и то же сообщение «Неверный email или пароль», чтобы по ответу нельзя было узнать, зарегистрирован ли адрес. После успешного входа сервер выдаёт токен (п. 2.3.2), и дальше приложение отправляет его вместо пароля.

### 2.6.2 Сессия и выход

Если при входе отмечено «Запомнить меня», идентификатор пользователя и токен сохраняются в `shared_preferences`. При следующем запуске Splash запрашивает `GET /api/me`: если сервер принял токен, открывается главная; если ответил `401` (токен устарел или аккаунт удалён), сохранённая сессия стирается и открывается экран входа. Если сервер недоступен, тоже открывается экран входа, где можно проверить адрес сервера, но сессия не стирается: после восстановления связи вход выполнится без пароля. При выходе приложение отправляет `POST /api/auth/logout`, и сервер удаляет токен; затем стираются сохранённые данные сессии, отменяется ежедневное напоминание, а роутер открывает экран входа. Выход выполняется даже без связи с сервером.

### 2.6.3 Удаление аккаунта

Удаление аккаунта необратимо, поэтому требует повторного ввода пароля: приложение отправляет `DELETE /api/me` с паролем в теле запроса. Сервер проверяет пароль и удаляет строку пользователя, а планы, занятия, темы, заметки, избранное, история Pomodoro и токены входа удаляются каскадно правилами внешних ключей. Затем выполняется выход.

### 2.6.4 Создание плана и работа с ним

Онбординг ведёт контроллер `OnboardingController`: он хранит выбранное направление, ответы теста и настройки расписания между шагами. На экране предпросмотра `PlanService.preview` рассчитывает план без сохранения. `PlanService.createPlan` рассчитывает план в приложении и отправляет его одним запросом `POST /api/plans`; сервер сохраняет темы и занятия в одной транзакции и делает новый план активным. Отметка занятия — запрос `PUT /api/sessions/{id}/done`; после ответа сервера главная, план и статистика загружают данные заново (п. 2.3.3).

### 2.6.5 Напоминания и уведомления

Ежедневное напоминание реализовано пакетом flutter_local_notifications [27]. Время напоминания хранится в профиле пользователя и пересчитывается в UTC, поэтому дополнительный пакет определения часового пояса не нужен. При окончании интервала Pomodoro показывается мгновенное уведомление. В Android-проекте объявлены приёмники плагина для показа запланированных уведомлений и их восстановления после перезагрузки, разрешение `RECEIVE_BOOT_COMPLETED` и белый значок уведомлений. На Windows плагин не поддерживает ежедневное повторение без установщика MSIX, поэтому переключатель напоминания в настольной версии недоступен и подписан «Доступно в версии для Android и iOS»; мгновенные уведомления работают.

Сервис уведомлений скрыт за интерфейсом `ReminderService`. В тестах вместо него подставляется заглушка, которая записывает вызовы в журнал, поэтому тесты проверяют, что напоминание запланировано, не показывая настоящих уведомлений.

### 2.6.6 Обработка ошибок

Ошибки, понятные пользователю (занятый email, неверный пароль, пустое название), передаются исключением `AppException` с русским текстом и выводятся под полем формы или во всплывающем сообщении. Сервер проверяет те же правила и возвращает тот же текст в ответе `400`, а клиент API превращает его в `AppException`, поэтому для пользователя не важно, где именно найдена ошибка. Ошибки связи с сервером обрабатываются отдельно (п. 2.3.3). Повреждённый файл каталога превращается в понятное сообщение вместо падения приложения. Ошибки платформы при работе с уведомлениями не прерывают выход из аккаунта.

## 2.8 Сборка и развёртывание

Сборка автоматизирована в GitHub Actions [28] (файл `.github/workflows/build.yml`). При каждой отправке кода в репозиторий выполняются:

1. проверка форматирования кода, статический анализ и все модульные и виджет-тесты;
2. интеграционный тест настоящего приложения в Linux на виртуальном экране;
3. сборка релизного APK для Android (`flutter build apk --release`) [20];
4. сборка релизной версии для Windows (`flutter build windows --release`) [21];
5. сборка для iPhone на компьютере macOS без подписи (`flutter build ios --release --no-codesign`) и упаковка в файл IPA;
6. сборка программы-сервера API для Windows (`dart build cli`) вместе с каталогом тем и файлом «Запустить сервер.bat».

Готовые файлы сохраняются как артефакты сборки. Когда на странице Releases репозитория публикуется новый релиз (например, `v1.0.0`), сборка запускается для него и прикладывает APK, архив для Windows, IPA для iPhone и архив сервера к релизу, откуда их можно скачать без входа в GitHub.

Для установки на телефон нужно скачать файл `marshrut-release.apk`, открыть его и разрешить установку из этого источника. Релизный APK подписан отладочным ключом: для установки на свой телефон этого достаточно, для публикации в Google Play нужен собственный ключ подписи. Версия для Windows распространяется как архив: его нужно распаковать и запустить `marshrut.exe`. На iPhone приложение устанавливается с компьютера на Windows программой Sideloadly, которая подписывает IPA бесплатным Apple ID пользователя; такая подпись действует 7 дней, после чего установку повторяют. Публикация в App Store требует платного аккаунта разработчика Apple и в учебном проекте не использовалась.

Сервер API распространяется как архив: его нужно распаковать и запустить «Запустить сервер.bat», разрешить доступ в брандмауэре Windows и ввести на телефоне адрес, который показывает окно сервера. Пошаговые инструкции для пользователя — в файлах `docs/Сервер_API` и `docs/Установка_на_iPhone` репозитория. Для самостоятельной сборки достаточно установленного Flutter SDK: команды приведены в README.
